Architecture Teardown & Reference Design

Cell Architecture Studio, and how to build one that scales.

A teardown of the live interactive 3D cell-biology explorer — what it's made of and how it behaves — followed by a reference architecture for building the same class of tool for classrooms and research groups without it falling over at scale.

01The teardown

What the app actually is

Cell Architecture Studio is a single-page web app that renders scientifically-sourced 3D cell models in the browser and lets a learner rotate, cross-section, label, and compare them — with an AI tutor answering questions grounded in whatever organelle they're currently looking at. It's a client-heavy, asset-heavy, thin-backend application: nearly all the intelligence lives in the browser bundle, and the only server dependency is a small tutoring endpoint that degrades gracefully to canned answers when it's unavailable.

Reading the shipped bundle and the public repo, the specimen library covers seven cell types — plant, animal, white blood cell, neuron, epithelial, bacteria, and muscle — each with positioned, labelled organelles, view modes (native material, cross-section, microscope), an animation layer, and a side-by-side comparison workflow.

Asset pipeline

Compressed models + procedural fallback

Specimens are .glb meshes (several sourced from the NIH 3D print exchange) compressed with DRACO and streamed lazily via useGLTF behind a Suspense boundary with a loading overlay. If a model fails or the network is slow, the app falls back to procedurally generated geometry so the lesson never shows an empty canvas.

Each specimen is a config object: organelle ids, 3D label anchor coordinates (e.g. {nucleus:[.76,.32,.26]}), descriptions, and per-cell comparison metadata. Adding a cell is authoring data + a mesh, not writing new render code — the single most important property for scaling content.

AI tutor

Context-grounded Q&A endpoint

The panel POSTs the question plus the current organelle context to /api/tutor with a 9-second AbortController timeout. The response is validated (answer must be a non-empty string) and tagged source: "api" | "local". On any failure it returns a local fallback answer — the tutor is an enhancement, never a hard dependency.

03Why it's built this way

The design decisions worth copying

Graceful degradation

Two independent fallbacks

Procedural geometry when a mesh fails; a local answer when the tutor API fails. A lesson in a school with flaky Wi-Fi still works. Copy this — it's the difference between a demo and a classroom tool.

Thin, stateless backend

One tiny endpoint

The only server is /api/tutor. No database, no auth, no session state in the critical path. The whole experience is a CDN-served static bundle plus one function — cheap to run and near-impossible to take down.

Content as data

Specimens are config, not code

Cells, organelles, and label anchors are declarative objects. A biology contributor can extend the library without touching the render engine — the property that makes the catalogue scalable.

Credible assets

Real scientific models

Meshes are sourced from the NIH 3D collection with documented provenance. For an education/research tool, "where did this model come from" is a feature, not a footnote.

05Grow into it

Three tiers, one codebase

Don't build the institutional version first. Each tier is the previous one plus a bounded set of additions — the client stays the same, the backend grows behind it.

06Where it breaks

The four things that bite at scale

Everything above is easy to draw. These are the constraints that actually decide whether it holds up.

1 · 3D assets are your real payload budget

A rich cell mesh is megabytes even compressed. Ship DRACO for geometry and KTX2/Basis for textures, generate LODs, lazy-load per specimen behind Suspense, and preload only the next likely model. Budget for the low-end device — a $150 Chromebook or a mid-range phone is the median classroom GPU, not your laptop. Cap texture sizes and polygon counts per LOD accordingly.

2 · The AI tutor is where the bill grows

A per-question LLM call is fine for a demo and ruinous for a district. Contain it: a semantic cache (identical/similar organelle questions hit the same answer), streaming responses so latency feels low, hard per-user and per-org rate limits, and — critically — keep the local fallback the live app already has, so a cache miss under load degrades instead of failing. Ground answers in the current organelle context to keep prompts short and answers accurate.

Recommendation

Back the tutor with Claude (e.g. a fast model like Claude Haiku 4.5 for cached, high-volume Q&A and a stronger model for open-ended questions). Send the current specimen + organelle as structured context, cap output tokens, and cache on a normalized (specimen, organelle, question) key. When you wire this up, load the claude-api skill for current model IDs, pricing, streaming, and prompt-caching details rather than hard-coding them.

3 · Content pipeline decides who can contribute

If adding a specimen means a developer editing TypeScript, your catalogue stalls. Make specimens authored data — a manifest schema (organelle ids, label anchors, descriptions, provenance, translations) validated in CI, with meshes run through an automated transcode step. A biologist or grad student should be able to open a PR that adds a cell. This is the same "content as data" property the live app already leans on; institutionalize it.

4 · Accessibility & low-bandwidth aren't optional in education

A WebGL-only app excludes screen-reader users and dies on bad networks. Pair every 3D scene with a text/2D equivalent (the organelle data you already have makes this cheap), respect prefers-reduced-motion, ensure keyboard navigation of labels, and keep the procedural fallback path healthy. For research/institutional use, plan for offline or LMS-embedded delivery.
